# Phase 10 — Graph Editing + Connections

## 1. Executive Summary

**Supposed to achieve.** Roadmap §16 (`docs/roadmap-frontend.md`): turn the Phase 07–09 draft editor into a complete graph editing system. Users must be able to build a full graph visually, invalid connections must be prevented or marked early in the UI, and the backend stays authoritative.

The session prompt added:
- reconnecting edges;
- explicit feedback for valid, incompatible and duplicate connections, missing required inputs and invalid operations;
- tested persistence and reload consistency;
- the instruction to implement, test and document any missing backend API.

**Actually implemented.**
- **Frontend editing** (all in `frontend/src/features/editor/`):
  - drag-to-connect between ports;
  - reconnecting an edge by dragging either end;
  - edge selection and deletion;
  - node delete (a node takes its edges with it);
  - node duplicate;
  - multi-selection: Ctrl/⌘-click, Shift box, Ctrl/⌘+A;
  - keyboard shortcuts.
- **Connection feedback:**
  - during a drag, ports that fit grow and turn green, the others fade, and the line is solid or dashed red;
  - a refused drop shows a toast with the reason;
  - invalid stored edges get a text label;
  - unconnected required inputs are named on the card.
- **Accessible editing path:** a new `ConnectionsPanel` with edge lists, Remove buttons and a "New connection" form.
- **Backend:** the port type rule existed only as Python code (`ports_compatible`). It is now also published as data: `GET /api/v1/nodes` returns `port_compatibility`, generated from that function. The frontend uses it and does not re-implement the rule.

**Resulting state.** Every new operation is one undo step and is saved through the existing draft save, autosave and revision-conflict handling. A full-stack test against the real backend connects `core.input → core.log → core.output` by dragging and saves. The backend stores the edges, `POST /workflows/{id}/validate` returns `{valid: true, issues: []}`, and a page reload shows the same graph.

**Acceptance criteria.** All three roadmap criteria pass (§14). Limitations remain, for example no cycle pre-check and no canvas-level keyboard connecting (§20).

**Phase Status:** COMPLETE WITH LIMITATIONS

## 3. Scope Implemented

### Backend / Domain
- `akasha.domain.graph_validation.port_signature(port)`: a port's value shape. It is the `PortType` value, with a `[]` suffix when `multiple` (e.g. `"string[]"`).
- `akasha.domain.graph_validation.port_compatibility()`: the `ports_compatible` rule as a dict from each output signature to the list of input signatures it may feed. It is generated by calling `ports_compatible` on every pair of (type × multiple) shapes: 20 shapes, so 400 pairs.

### Backend / API
- `akasha.api.nodes.NodeCatalog` gains a required field `port_compatibility: dict[str, list[str]]`.
- `list_node_types` fills it from `port_compatibility()`.

### Frontend / API layer
- `src/api/nodes.ts`:
  - `nodeCatalogSchema` gains `port_compatibility: z.record(z.string(), z.array(z.string()))`;
  - new exported type `NodeCatalog`.

### Frontend / Editor state (`editorState.ts`, `useDraftEditor.ts`)
- **New state:** `edgeSelection: string[]` (edge keys). It is not part of undo history.
- **Changed action:** `select` is now `{nodeIds?, edgeKeys?}`; a kind that is left out keeps its selection.
- **New actions:**
  - `connect {edge}`;
  - `reconnect {from, edge}`: replaces the edge at the same list index and remaps `edgeSelection`;
  - `delete {nodeIds, edgeKeys}`: removes nodes, every edge touching them, and the given edges, as one step;
  - `duplicate {ids}`: copies the selected nodes and the edges between them, offset by `PASTE_OFFSET`; the clipboard is untouched.
- **Shared helpers:**
  - `copyOf`: shared by copy and duplicate.
  - `insertCopies`: shared by paste and duplicate.
  - `existing(state, graph)`: prunes both selections on undo, redo and delete.
  - `savable(graph, edge)`: refuses self-edges, duplicates and dangling ends.
- `useDraftEditor` gains `duplicate()`. Ids come from the shared `freshIds` helper, so the reducer stays pure.

### Frontend / Connection rules (`connections.ts`, new)
- **`connectionProblem(graph, edge, rules, replacing?)`** returns a `{code, message}` or `null`. Checks run in this order:
  1. `self`
  2. `unknown_node`
  3. `duplicate`
  4. `unchecked` (no catalog)
  5. `unknown_type`
  6. `unknown_port`
  7. `occupied` (a second edge into a non-`multiple` input)
  8. `incompatible` (looked up in `port_compatibility`)

  `replacing` excludes the edge that is being reconnected.
- **`missingInputs(nodeId, definition, edges)`**: required inputs with no incoming edge.
- **`PROBLEM_LABELS`**: short reason texts for edge labels and select options.

### Frontend / Canvas and UI
- **`GraphCanvas.tsx`:**
  - Handles are connectable.
  - `isValidConnection` and `onConnect` go through `connectionProblem`.
  - `onConnectEnd` and `onReconnectEnd` report refused drops via `onRefuse`.
  - `edgesReconnectable` is on; the edge being reconnected is held in the `reconnecting` ref.
  - Edges are selectable and focusable, with `ariaLabel` "Connection from {node} {port} to {node} {port}[, invalid: …]".
  - Invalid stored edges get the `edge-invalid` class and a `label`.
  - `onEdgesChange` handles edge selection.
  - A `CheckContext` gives each `DraftNode` the current check. With `useConnection`, each node marks its ports `fit: compatible | incompatible` during a drag.
- **`NodeCard.tsx`:**
  - Ports are `CardPort` objects: `{name, type?, required?, fit?}`.
  - Each port shows its type signature.
  - A required input shows `*` (with `aria-hidden`) plus the screen-reader text " (required)".
  - Each handle gets a `port-compatible` or `port-incompatible` class.
  - A "Missing required input: …" line is added.
- **`ConnectionsPanel.tsx` (new):** shown for a single selected node.
  - Inputs and outputs, each with its connected edges and a Remove button (with an `aria-label` naming both ends).
  - "Not connected" for empty ports, and the missing-required-inputs warning.
  - A "New connection" form: "From output" select, and a "To input" select over every input of every other node. An option that cannot take the output is disabled, with its reason in parentheses.
- **`EditorPage.tsx`:**
  - Toolbar buttons "Duplicate" (`aria-keyshortcuts` Control+D Meta+D) and "Delete".
  - Keyboard handling (see §8).
  - The canvas region gets `tabIndex={-1}`.
  - Deleting from the canvas moves focus to the canvas region first.
  - Refused connections show a warning toast "Not connected" with the reason.
  - `NodeInspector` and `ConnectionsPanel` sit in one `Fragment` keyed by node id.
  - The catalog-failure alert now says nodes cannot be "added or connected".
  - The editor receives `rules: ConnectionRules`, which bundles the catalog map and `port_compatibility`.
- **`graphView.ts`:**
  - new `portSignature`, `sameEdge` and `cardPort(port, input)`;
  - `portsOf` now returns `CardPort[]` lists.
- **`NodeLibrary.tsx`:** the preview card uses `cardPort`, and the query type is `UseQueryResult<NodeCatalog>`.

## 5. Architecture Changes

### 5.1 The port compatibility rule is published as data

#### Decision
The backend serves the result of `ports_compatible` as a table in the node catalog. The frontend looks connections up in that table.

#### Context
- AGENTS §4 and frontend AGENTS §7 forbid re-implementing "Node compatibility rules" in the frontend.
- Frontend AGENTS §32 asks that the editor check port type fit while connecting.
- React Flow calls `isValidConnection` synchronously, on every handle the pointer passes, so the check cannot be a request.
- Before this phase, the rule existed only in Python. The catalog exposed `type` and `multiple` per port, but not how they combine.

#### Chosen Approach
`port_compatibility()` enumerates all 20 (type, multiple) shapes on both sides and keeps the pairs `ports_compatible` accepts. `GET /nodes` returns the result next to `items`.

#### Alternatives Considered
- (a) A TypeScript copy of the rule. It diverges silently.
- (b) A per-connection check endpoint. It is too slow on every hover.
- (c) An `accepts` list on each input port. It repeats the same data per port.
- (d) A separate endpoint. That is a second query and loading state for data that is only used with the catalog.

#### Reason
- This is the smallest change that keeps one definition of the rule.
- The data is static and small (20 keys).
- It loads with the catalog the editor already fetches.

#### Consequences
- Changes to `ports_compatible` reach the editor without a frontend change. The backend test enforces equality with the function for all 400 pairs.
- `port_compatibility` is a required catalog field: a frontend of this phase cannot parse a catalog from an older backend (§21).

### 5.2 What the frontend pre-checks itself

#### Decision
Besides the table lookup, `connectionProblem` checks:
- **Self, duplicate and dangling edges.** The backend refuses to store these (`Edge.__post_init__` and `Graph.add_edge` in `akasha.domain.graph`). The reducer refuses them too, via `savable`, because they would make the draft unsavable.
- **A second edge into a non-`multiple` input.** This uses the contract's `multiple` flag and matches `validate_graph`'s `fed_inputs` check.
- **Unconnected required inputs.** This uses the contract's `required` flag.

#### Context
All three are read directly from contract fields, so no hidden backend logic is copied.

#### Chosen Approach
They are UX pre-checks only. `/validate` and publish re-check everything. Cycles are not pre-checked.

#### Alternatives Considered
- Publishing the single-input and required rules as data too. Rejected: they are plain field semantics, and there is nothing to generate.
- A cycle check in the frontend. Rejected for now: graph validity belongs to the backend, and loop nodes may later allow marked cycles (`_check_cycles` ponytail note).

#### Reason
These checks catch the most common errors at the moment of drawing. They duplicate no rule logic.

#### Consequences
If the backend changes the meaning of `multiple` or `required`, `connections.ts` must follow. It is the only place that encodes them on the frontend.

### 5.3 Edge selection in editor state

#### Decision
`EditorState.edgeSelection` holds selected edge keys (`edgeKey`), next to `selection` (node ids).

#### Context
Deleting edges needs selected edges. React Flow is controlled, so selection must come from the editor state.

#### Chosen Approach
The reducer prunes edge selection whenever the graph changes through undo, redo, delete or reconnect. `select` updates only the kinds it is given.

#### Alternatives Considered
A single mixed selection list. Rejected: node ids and edge keys are different kinds, and every consumer would need to tell them apart.

#### Reason
This is the smallest change; the existing node selection semantics stay intact.

#### Consequences
Code that clears selection (e.g. `focusNode`) must pass `edgeKeys: []` explicitly.

## 8. Implementation Details

### Connecting by drag (`GraphCanvas`)
- **Candidate check.** React Flow calls `isValidConnection(connection)` per candidate handle. `toEdge` converts the connection; it returns null while a handle id is missing. The result goes to `check`, which is `connectionProblem(graph, edge, rules, reconnecting.current)`.
- **Per-port fit.**
  - Each `DraftNode` subscribes to `useConnection`, reduced to a `type\nnodeId\nport` string or `null`.
  - Nodes therefore re-render only when a drag starts or ends, not on every pointer move.
  - Every port on the opposite side gets `fit` from `check`.
  - The newline separator avoids clashes with port names that contain spaces.
- **Line state.** React Flow sets `.valid` or `.invalid` on `.react-flow__connection`; the CSS styles it.
- **Drop.**
  - A valid drop fires `onConnect`, which dispatches `connect`.
  - An invalid drop on a handle: `onConnectEnd` gets `FinalConnectionState` with `isValid === false` and `toHandle` set. `refused` rebuilds the source/target edge from `fromHandle` and `toHandle` and calls `onRefuse(problem)`. `EditorPage` shows a warning toast "Not connected" with the message.
  - A drop in empty space does nothing.

### Reconnect
- `onReconnectStart` stores the edge in `reconnecting`. While the drag lasts, all checks ignore that edge, so it can return to its own ports and is not "occupied" by itself.
- `onReconnect` dispatches `reconnect`.
- `onReconnectEnd` reports a refused drop and clears the ref.
- A drop in empty space keeps the edge unchanged.

### Keyboard
Handled by `onKeyDown` on the editor container. Text inputs are ignored (`isTextInput`).

| Shortcut | Works where | Action |
|---|---|---|
| Ctrl/⌘+Z | anywhere in the editor (Phase 07) | Undo |
| Ctrl/⌘+Shift+Z, Ctrl+Y | anywhere in the editor (Phase 07) | Redo |
| Ctrl/⌘+C | anywhere in the editor (Phase 07) | Copy |
| Ctrl/⌘+V | anywhere in the editor (Phase 07) | Paste |
| Ctrl/⌘+S | anywhere in the editor (Phase 07) | Save |
| Ctrl/⌘+D | anywhere in the editor | Duplicate (new) |
| Ctrl/⌘+A | only inside the canvas region | Select all (new) |
| Delete, Backspace | only inside the canvas region, without modifiers | Delete selection (new) |
| Escape | only inside the canvas region, without modifiers | Clear selection (new) |

- **Canvas-only keys.** Scoping Delete, Backspace, Escape and Ctrl/⌘+A to the canvas keeps Backspace on a focused inspector button from deleting a node, and keeps Ctrl/⌘+A as the browser's select-all elsewhere.
- **React Flow's own deletion** stays off (`deleteKeyCode={null}`). Deletion goes through the reducer.

### Focus
- The canvas `section` has `tabIndex={-1}`, so a click on the empty pane focuses it and shortcuts keep reaching the editor. Verified in the browser: `document.activeElement` is "Graph canvas" after a pane click.
- `deleteSelection` moves focus to the canvas region when focus is inside it, because the focused node or edge element is about to be removed.

### Stored edge feedback
- For each edge, `connectionProblem(graph, e, rules, e)` runs on every render of the edge list.
- Problems are shown except `unchecked` (catalog not loaded) and `unknown_type` (the node card already says "Unknown node type").
- A shown problem means: the class `edge-invalid`, a `label` from `PROBLEM_LABELS`, and an accessible name ending in ", invalid: {message}".

### Connections panel
- The source output is the chosen output if it still exists, else the first output.
- Target options are built from `portsOf` of every other node. Each option's `problem` comes from `connectionProblem`.
- The chosen target is dropped when it becomes invalid, for example after a different output is chosen or another edge took the input.
- Submit dispatches `connect`. Remove dispatches `delete` with a single edge key.

### Persistence
The mechanism is unchanged from Phase 07. Edges are part of `draft.graph` in `PUT /api/v1/workflows/{id}` with `expected_revision`. Autosave (1.5 s), the single-flight save, the 409 conflict flow, the leave guard and "the undo stack survives saves" all cover the new operations without extra code.

### Purity
The reducer generates no ids and reads no time. New ids for duplicate and paste come from `useDraftEditor.freshIds`.

## 9. Findings

### Finding 1 — The port rule had no form the frontend could use
- **Impact:** HIGH
- **Resolution:** FIXED
- **Notes:** Without it, the acceptance criterion "invalid connections prevented early in the UI" could only have been met by copying `ports_compatible` into TypeScript, which AGENTS §4 forbids. The rule is now published (§5.1). The roadmap assumed node contracts alone suffice; they contain the port fields but not the rule that combines them.

### Finding 2 — Sibling panels with duplicate React keys left stale panels on screen
- **Impact:** MEDIUM
- **Resolution:** FIXED
- **Notes:** Seen in a full-stack screenshot: "Settings: Input", "Settings: Log" and "Settings: Output" were all shown after adding three nodes. Details in §10.

### Finding 3 — Keyboard delete lost focus
- **Impact:** MEDIUM
- **Resolution:** FIXED
- **Notes:** After Delete removed the focused edge, focus fell to `<body>`, which is outside the editor container, so Ctrl/⌘+Z did nothing. Found by the new E2E test.

### Finding 4 — jsdom has no `SVGElement.getBBox`
- **Impact:** LOW
- **Resolution:** WORKAROUND
- **Notes:** React Flow edge labels (`EdgeText`) measure their text, which crashed the route in jsdom. A fixed-size stand-in was added to `src/test/setup.ts`, alongside the Phase 07 layout stand-ins. Label geometry is verified in Playwright only.

### Finding 5 — Edge accessible names made existing test queries ambiguous
- **Impact:** LOW
- **Resolution:** FIXED
- **Notes:** Edges are now focusable `group`s named "Connection from Lead in …". Five `EditorPage.test.tsx` queries using `/Lead in/` or `/core\.log/` were anchored with `^`. What they test is unchanged.

### Finding 6 — Contract coverage counts every function exported from `src/api/*`
- **Impact:** LOW
- **Resolution:** FIXED
- **Notes:** `contract.node.test.ts` "every service function is covered" failed when `portSignature` was exported from `api/nodes.ts`. It is feature logic, so it moved to `features/editor/graphView.ts`.

### Finding 7 — `dragTo` drop positions are unreliable in the full-stack layout
- **Impact:** LOW (test design)
- **Resolution:** WORKAROUND
- **Notes:**
  - The editor's canvas is about 310–400 px wide inside the page's max width.
  - Dragging library items that sit far down the list scrolls the page, so dropped nodes overlapped.
  - A later press then hit a node body instead of a handle.
  - The full-stack connection test now seeds three nodes through `PUT /workflows/{id}`. Node insertion by drag stays covered by Phase 08 tests and the mocked E2E.
  - Product behavior is unaffected.

### Finding 8 — Frontend unit tests are sensitive to CPU load
- **Impact:** LOW
- **Resolution:** OPEN (pre-existing)
- **Notes:**
  - One `vitest run` made while the backend `pytest` suite ran in parallel failed the first test of `EditorPage.test.tsx` and `NodeInspector.test.tsx`. Both were 1 s `findBy` timeouts during cold start.
  - Two isolated reruns passed 289/289.
  - This matches Phase 08 finding 3 (`App.test.tsx`).
  - Not caused by this phase's logic, but the heavier editor render makes the first test slower.

## 11. Fixes Applied

1. **Stale panels.**
   - Symptom: three settings panels visible.
   - Root cause: duplicate sibling keys.
   - Implementation: keyed `Fragment` in `EditorPage.tsx`.
   - Verification: new component test (fails with the old code, passes with the fix); full-stack suite 8/8.
2. **Focus after delete.**
   - Symptom: Ctrl/⌘+Z ignored after Delete.
   - Root cause: focus fell to `<body>`.
   - Implementation: `canvasRef.current.focus()` in `deleteSelection` when focus is inside the canvas.
   - Verification: E2E passes.
3. **Feedback styles.**
   - Symptom: no visible fit or invalid state in screenshots.
   - Root cause: missing CSS.
   - Implementation: `index.css`.
   - Verification: a zoomed screenshot shows a green enlarged compatible port, a faded incompatible port, and a dashed red line.
4. **Unknown node types flagged their edges.**
   - Symptom: in the first iteration, edges of nodes whose type is not in the catalog were labelled "unknown port", which was misleading.
   - Root cause: the port lookup ran on a missing definition.
   - Implementation: a separate `unknown_type` code, not shown on edges.
   - Verification: `connections.test.ts` "refuses ports the contract lacks and nodes of unknown type"; `EditorPage.test.tsx` fixtures with `core.log` missing from the catalog render without an edge label.
5. **Accessibility of the required marker.**
   - Symptom: `aria-label` on a plain `span` is ignored by assistive technology.
   - Implementation: `aria-hidden` star plus `sr-only` " (required)".

## 16. Performance Considerations

No measurements were made.
- **Stored edges.** `connectionProblem` runs once per stored edge on each change of graph, edge selection or rules. Each call scans nodes and edges: O(E·(N+E)) per render.
- **During a drag.**
  - Each node runs one check per port on the opposite side, only when a drag starts or ends (the `useConnection` selector returns a stable string).
  - React Flow calls `isValidConnection` per hovered handle.

- **Payload.** The catalog response grows by the 20-key table, about 1–2 KB.
- **Scale.** Acceptable for drafts of tens to hundreds of nodes by inspection. Large-graph measurement belongs to Phase 24.

## 20. Known Limitations

1. **Cycles are not prevented while drawing.** `/validate` and publish report them.
2. **No keyboard connecting on the canvas itself.** React Flow handles are not keyboard targets; the Connections panel is the keyboard and screen-reader path.
3. **The panel creates edges only from the selected node's outputs.** To make an edge into a node, select its source node.
4. **An occupied single input is refused, never replaced.** The message says to delete or reconnect the existing edge.
5. **Reconnect dropped on empty space keeps the edge.** Removing it needs Delete or Remove.
6. **The refusal toast is transient.** Lasting problems (missing inputs, invalid stored edges) are shown as text on the graph.
7. **Copy/paste uses the internal clipboard** (Phase 07).
8. **The full-stack connection test seeds node positions through the API** (Finding 7). Visual node insertion is covered elsewhere.
9. **Ctrl/⌘-click multi-selection** relies on React Flow defaults and has no dedicated test.

## 22. Architectural / Product Decisions

- **Rules that must not be copied into the frontend are published as data**, generated from the backend function. The backend test proves the table and the function agree. Use this pattern again for similar rules.
- **The reducer refuses only unsavable edges** (self, duplicate, dangling). Type fit is checked by the callers: drag, panel. A stored edge that no longer fits stays in the graph and is labelled, never silently dropped.
- **Delete, Escape and select-all act only inside the canvas.** Form controls and the page keep their usual keys.
- **Transient vs. lasting feedback.** Refusals are toasts. States that persist in the graph (missing inputs, invalid edges) are text on the canvas and in the panel. Colors are always accompanied by size, dashes or text.
- **Edges are identified by `edgeKey`** (`source:port->target:port`) for React Flow ids and selection. The domain has no edge ids, and duplicates are impossible.
- **The side panels share one key per node.** Panels showing per-node local state must sit under the same keyed `Fragment`.
